# 1. 背景与问题

`runtime::Engine` 目前是一个"空壳单例"：它只负责初始化 Logger、托管一个 `IGame`，
`run()`/`render()`/`tick()` 基本是空的，既不是主循环的持有者，也不是各子系统的所有者。
真正把系统串起来的"组合根"在 [sources/engine/launcher/Main.cpp](sources/engine/launcher/Main.cpp) 里，
每帧逻辑以 lambda 形式塞进 `App.setFrameHook(...)`，主循环则由 `ui::GenericApplication::run()`
在跑。结果是各子系统"各自为政"，没有按照 Engine 统一管理。

现状清单：

| 子系统 | 现状 | 当前由谁驱动 |
|---|---|---|
| `runtime::Engine` | `run()/render()/tick()` 基本为空，只 `attachGame` + 初始化 Logger | 基本没被真正使用 |
| `ModuleLoader` / `modules::PluginManager` | 空壳单例 | 无人 |
| `runtime::Logger` | 单例，Engine 里直接 `Logger::self()` | Engine（仅 preinitialize） |
| `ui::GenericApplication`（UI/Editor） | 独立单例，自己 `initialize()`/`run()` 主循环，析构里关 FontService | 自己在 `run()` 里跑事件循环 |
| `ui::IGenericPlatform` / `SdlPlatform` / `SdlWindow` | 平台抽象错放在 `ui::` 命名空间，由 `GenericApplication::initialize()` 里 `createPlatform()` 创建 | GenericApplication |
| `ui::FontService` | 独立单例 | GenericApplication |
| `runtime::renderer::RendererServer` | 独立单例，持有 RHI/设备/交换链/渲染循环 | Main.cpp 手动 `initialize()`/`shutdown()` |
| `runtime::Camera*` | `CameraManager.hpp` / `CameraDirector.hpp` 是空文件 | 无人 |
| `game::Game` / `DemoGame` | 经 `Engine::attachGame()` 托管 | Engine（仅生命周期，无主循环） |

本设计的目标是：**让 Engine 成为唯一编排主体**，统一拥有并驱动上述所有子系统的生命周期，
消除散落在 Launcher 与 UI 里的编排逻辑。

# 2. 目标

1. Engine 拥有一个**子系统注册表**，按固定阶段统一驱动每个子系统的
   `preinitialize / initialize / postinitialize / tick / shutdown`。
2. `Engine::run()` 成为**唯一主循环**：轮询平台事件 → 路由 UI/Editor → tick 世界/游戏 →
   渲染（RDG）→ 呈现 → 泵日志。`GenericApplication::run()` 不再持有事件循环。
3. 平台抽象（`IGenericPlatform`/`IGenericWindow`/事件）从 `ui::` **上移为引擎级 platform 层**，
   由 Engine（或其引导的 `EngineMain`）构造并注入给 UI 与 Renderer。
4. `Main.cpp` 瘦身为纯引导：解析命令行 → 构造 Platform → 构造 Engine → attach 宿主（Game/Editor）→ `run()`。
5. 依赖方向保持单向：`Game -> Engine`、`UI/Editor -> Runtime/Platform`，Engine 核心不反向依赖 Editor/UI。

# 3. 设计原则

- **Engine 是主体**（与 [logs/引擎的框架.md](logs/引擎的框架.md) 的 [Engine] 立场一致）：
  游戏/编辑器是引擎运行环境里的"执行实体"，生命周期由引擎控制。
- **依赖反转**：Engine 通过注册表驱动子系统，不直接 `#include` UI/Editor 头文件，
  避免 runtime 反向依赖 editor，也避免出现循环依赖。
- **生命周期对称**：初始化顺序与关闭顺序严格相反（后初始化先关闭）。
- **单例收敛**：现有 `Logger::self()`、`RendererServer::self()`、`FontService::self()` 等单例
  可以保留为"进程内唯一实例"，但**其生命周期（start/stop、initialize/shutdown）必须由 Engine 编排**，
  不再由使用者各自调用。

# 4. 目标架构总览

```text

        │  各自提供 main(...) 后统一进入
        ▼

        │  1. 解析 CommandLine

        │  3. 构造 Engine 并注册子系统
```

# 5. 子系统模型（ISubsystem）

新增引擎级子系统契约，所有受 Engine 管理的系统实现它：

```cpp
// runtime/engine/includes/engine/ISubsystem.hpp
namespace runtime
{
class ISubsystem
{
public:
    virtual ~ISubsystem() = default;

    // 基础设置与平台相关设置（日志、线程池、平台运行时、配置加载）。
    virtual void preinitialize() {}
    // 正式初始化（窗口、RHI/渲染器、UI、字体、编辑器；未来 Network/Audio/Physics）。
    virtual void initialize() {}
    // 第一帧前的收尾（引擎自身就绪后、游戏 beginPlay 之前）。
    virtual void postinitialize() {}
    // 每帧推进；DeltaTime 秒。
    virtual void tick(float DeltaTime) {}
    // 逆序关闭，释放自身资源。
    virtual void shutdown() {}
};
}
```

Engine 持有有序注册表。注册通过 `ModuleLoader` 完成（见 §9），Engine 只接触
`ISubsystem` 这一窄接口，不感知具体子系统类型：

```cpp
// Engine 新增成员（概念）
class Engine final
{
public:
    // 按注册顺序依次驱动；shutdown 时逆序调用。
    void registerSubsystem(std::unique_ptr<ISubsystem> Subsystem);
    template<class T, class... Args> T& addSubsystem(Args&&...); // 工厂式注册，返回引用便于注入

    // 宿主契约：Game 与 Editor 都是"执行实体"。
    void attachGame(std::unique_ptr<IGame> Game);     // 已有
    void attachEditor(std::unique_ptr<IEditor> Editor); // 新增（Editor 与 Game 并列）
    ...
private:
    std::vector<std::unique_ptr<ISubsystem>> Subsystems;
    std::unique_ptr<IGame>    GameInstance;
    std::unique_ptr<IEditor>  EditorInstance;
};
```

# 6. 生命周期与初始化顺序

| 阶段 | 顺序（自上而下） | 说明 |
|---|---|---|
| `preinitialize` | Logger → Memory/ThreadPool → ConfigLoader(Engine.toml) → Platform | 日志最先可用；平台运行时随后；配置驱动后续阶段 |
| `initialize` | Platform(建窗口) → Renderer(RHI/设备/交换链) → UI/FontService → Editor | 窗口必须先于渲染器；UI/字体在渲染器之后；Editor 最后 |
| `postinitialize` | 引擎自身收尾 → Game/Editor 的 `postinitialize`（首帧） | 游戏 `beginPlay` 在此触发 |
| `run`（每帧） | `Platform.pollEvent` → 路由 UI/Editor → `tick(Δt)` 各子系统 + World + Game → `Renderer.renderFrameGraph()` → `present` → `Logger.pumpFrame` | 主循环，见 §7 |
| `shutdown` | 逆序：Game/Editor → UI/Font → Renderer → Window → Platform → Logger → Memory | 与初始化严格相反 |

> 这与 `Engine.hpp` 里 `preinitialize/initialize/postinitialize` 的注释已经对应；
> 本次只是把它们从"注释"落实为"真实编排"。

# 7. 主循环上移

把 `GenericApplication::run()`（[GenericApplication.cpp](sources/engine/launcher/editor/app/GenericApplication.cpp) 的
事件轮询 + `drawFrame` + `FrameHook`）上移为 `Engine::run()` 的核心循环：

```cpp
void Engine::run()
{
    while (!ShouldQuit)
    {
        const float DeltaTime = computeDeltaTime();

        // 1. 平台事件：由 Platform 子系统统一轮询，交给 UI/Editor 子系统路由。
        if (PlatformSubsystem)
            PlatformSubsystem->pumpEvents();   // 内部: while(auto e = Platform->pollEvent()) dispatch

        // 2. 推进：所有子系统 + 宿主(Game/Editor) + World。
        for (auto& Subsystem : Subsystems)
            Subsystem->tick(DeltaTime);
        tick(DeltaTime);                      // 驱动 GameInstance/EditorInstance

        // 3. 渲染：RDG 多 Pass（3D + UI）。
        RendererSubsystem->renderFrame();

        // 4. 日志手动泵帧（ManualFramePump 模式）。
        Logger::self().pumpFrame(512, std::chrono::milliseconds(10));
    }
}
```

`GenericApplication` 收敛为 **UI 子系统**：保留窗口创建、内容根控件树、字体会话、
`createTextWidget`、命中测试/输入派发等 UI 职责；**不再持有平台**（Platform 由 Engine 注入），
**不再拥有主循环**（由 Engine 调用其 `tick` 执行 `drawFrame` 并提交 UI 绘制列表）。

# 8. 平台层上移

## 8.1 目标

把平台抽象从 `ui::` 命名空间上移为引擎级 `runtime::platform`（模块 `Runtime::Platform`），
因为平台是 UI、Renderer、Engine 共同依赖的底层能力，不该挂在 UI 之下。

## 8.2 迁移映射

| 现文件（`sources/engine/launcher/generic/`） | 目标（`sources/engine/runtime/platform/`） | 命名空间 |
|---|---|---|
| `IGenericPlatform.hpp` | `IPlatform.hpp` | `ui::IGenericPlatform` → `runtime::platform::IPlatform` |
| `IGenericWindow.hpp` | `IWindow.hpp` | `ui::IGenericWindow` → `runtime::platform::IWindow` |
| `PlatformEvents.hpp` | `PlatformEvents.hpp` | `ui::Event/KeyEvent/...` → `runtime::platform::*` |
| `PlatformFactory.cpp` | `PlatformFactory.cpp` | `ui::createPlatform` → `runtime::platform::createPlatform` |
| `sdl/SdlPlatform.cpp` 等 | `sdl/SdlPlatform.cpp` 等 | `ui::SdlPlatform` → `runtime::platform::SdlPlatform` |

- 类型重命名：`IGenericPlatform → IPlatform`、`IGenericWindow → IWindow`、
  `GenericWindowPointer → WindowPointer`（可先只改命名空间、保留类型名以降低风险，二选一，见 §11）。
- `WindowConfigs`、`UISize`、`Rect`、`EWindowResizePolicy` 随之上移；`ui::Window` 改为持有
  `runtime::platform::IWindow`。
- `launcher/generic/` 只保留"入口解析"（`EngineMain` + `Entry/Native`、`Entry/SDL`），
  不再承担平台抽象职责。
- 依赖：`Runtime::Platform` 仅依赖 `Infra`（SDL 实现私有依赖 `SDL3::SDL3`）。
  UI/Editor、Renderer、Engine 都依赖它。

# 9. 依赖方向与 CMake 调整

目标依赖图（箭头 = 依赖）：

```text
Infra
  ▲
Runtime::Platform          ← 上移后的平台层
  ▲
Runtime::Logger / Camera / Renderer / Engine(core)
  ▲
Runtime::UI · Editor        ← UI/编辑器依赖 Platform + Renderer
  ▲
Game (经 runtime::IGame / IEditor 契约指向 Engine)
  ▲
Launcher (EngineMain + Entry)  ← 唯一切入点，链接所有模块
```

关键约束与调整：

1. **Engine 核心不反向依赖 Editor/UI**：子系统通过 `ModuleLoader` 的注册机制注入，
   Engine 只依赖 `ISubsystem` 抽象。当前 `ModuleLoader`/`PluginManager` 空壳正是为此预留。
2. **`Runtime::Engine` 依赖 Platform**：Engine 需要把平台注入 Renderer（窗口句柄）与 UI。
   在 [runtime/engine/CMakeLists.txt](sources/engine/runtime/engine/CMakeLists.txt) 增加
   `PRIVATE_DEPENDENCY Runtime::Platform`。
3. **`launcher/generic` 拆分**：`Generic::Generic` 拆为 `Platform::Platform`（上移到 runtime）
   + `Launcher::Entry`（入口垫片）。
4. **`Editor::Editor`** 依赖改为 `Platform::Platform + UI::UI + Renderer::UIBackend + ...`。
5. **`Game::Game`** 依赖方向不变（`Runtime::Runtime`），保持 `Game -> Engine` 单向。

# 10. 各子系统迁移要点

| 子系统 | 迁移动作 |
|---|---|
| **Logger** | 单例保留；Engine 在 `preinitialize` 调 `start(config)`（配置来自 `configs/Engine.toml`），`shutdown` 阶段 `stop()`；移除 Engine 外对 `start/pump` 的直接调用 |
| **Platform** | 由 `EngineMain` 构造、Engine 持有并注入；`GenericApplication::initialize` 不再 `createPlatform()`；事件轮询归 Engine 主循环 |
| **RendererServer** | 单例保留或改为 Engine 持有的子系统；`initialize(backend, window)` / `shutdown()` / `renderFrameGraph()` 全部由 Engine 在对应阶段调用，删除 Main.cpp 里的手动调用 |
| **UI (GenericApplication)** | 收敛为 UI 子系统：保留窗口/控件树/字体/输入派发；删掉 `run()` 与 `FrameHook`；`drawFrame` + 提交 UI 绘制列表由 Engine 每帧调用 |
| **Editor** | 引入 `IEditor` 宿主契约（与 `IGame` 并列），Main.cpp 里的编辑器界面构建代码移入 Editor 模块，由 Engine 在"启动 Editor 模式"时驱动 |
| **Game** | 保持 `attachGame(IGame)`；`tick` 纳入 Engine 主循环，删除 Main.cpp 手动驱动 |
| **Camera** | 将空文件 `CameraManager/CameraDirector` 落实为 `CameraSubsystem`（或并入 World），由 Engine 驱动 |
| **ModuleLoader/PluginManager** | 落实为子系统注册机制：各模块（UI/Renderer/Editor/Game）在模块加载时注册其子系统工厂，Engine 在 `preinitialize` 收集并实例化 |

# 11. 落地步骤（分阶段）

1. **Phase 0 — 基线**：确认当前构建/测试可复现（`cmake` 配置 + 构建 + 测试通过），作为回归基线。
2. **Phase 1 — 平台层上移**：纯目录/命名空间迁移（`ui::` → `runtime::platform`），行为不变；
   同步更新 CMake 目标与所有引用。全量编译验证。
3. **Phase 2 — 子系统骨架**：新增 `ISubsystem` + Engine 注册表；先把 `Logger`、`Platform`、
   `Camera` 接入，由 Engine 驱动其 `preinitialize/initialize/shutdown`。
4. **Phase 3 — 主循环上移**：`Engine::run()` 接管事件轮询 + tick + 渲染；`GenericApplication` 收敛为
   UI 子系统；删除 `FrameHook` 与 Main.cpp 的每帧 lambda。
5. **Phase 4 — Renderer 接入**：`RendererServer` 的 initialize/render/shutdown 归 Engine 编排。
6. **Phase 5 — 宿主契约与入口**：引入 `IEditor`（或统一 `IApplication`），Editor UI 构建移入 Editor 模块；
   新增 `EngineMain`，`Main.cpp` 瘦身为纯引导。
7. **Phase 6 — 模块注册机制**：`ModuleLoader`/`PluginManager` 落实为子系统注册，移除 Engine 对具体
   子系统的硬 include，完成依赖反转。

# 12. 风险与开放问题

- **破坏性命名空间变更**：`ui::IGenericPlatform` → `runtime::platform::IPlatform` 触及 UI、Renderer、
  Launcher 多处，需一次性完成并全量编译；可先保留类型名只改命名空间以降低风险。
- **单例 → Engine 持有**：`GSeedEngine` 宏与现有 `Logger::self()`/`RendererServer::self()` 调用点需同步梳理，
  避免"双所有权"或生命周期乱序。
- **事件循环上移后**：[editor_readme.md](editor_readme.md) 等文档中关于 `GenericApplication::run()`、
  生命周期的描述需同步更新；相关测试（`PlatformEvents`、`EditorHeadlessSmoke` 等）需适配。
- **Editor 与 Game 的边界**：建议引入 `IApplication` 统一契约（Game 与 Editor 都是宿主实体），
  还是 Editor 单独走 `IEditor`？需确认。
- **线程模型**：`RenderThread` 已存在；需明确 Engine 主循环（tick/渲染提交）在游戏线程、
  录制在渲染线程的边界，确保子系统 `tick` 与 `shutdown` 的线程亲和一致。
- **类型重命名范围**：`IGenericPlatform→IPlatform` 等是否一并执行，还是先仅上移命名空间，需在 Phase 1 定夺。
